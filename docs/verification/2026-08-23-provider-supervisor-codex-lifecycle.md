## Process and authority boundaries

- One common `ProviderAdapter` owns per-session slots, a supervisor identity, exact handle/profile correlation, `Launching` custody, confirmed-stop tombstones, typed safe-versus-uncertain launch outcomes, and bounded shutdown. Provider drivers report transport facts only.
- Codex binds verification to process creation: Linux/Android copy verified bytes into an executable `memfd` sealed against mutation, macOS and other Unix targets execute a byte-verified `0500` copy held in an explicitly verified private `0700` staging directory for the runtime lifetime, and Windows denies write/delete sharing while the selected image is held open. Staged identity is computed directly from the persisted open source identity and staged bytes. Linux/Android helper binding begins at `/proc/self/exe`; the macOS desktop supervisor opens its current image, matches device/inode against `lsof` mapped-text records, and privately stages those open bytes before launch. The server refuses provider custody without that proof. The guardian and anchor then re-execute exact bound helper bytes.
- Each current-profile runtime creates a generation-tokened exact room/session main lease and a separate lifetime lease before provider spawn. The independent Unix guardian is the provider launcher's actual parent, records the anchor group before continuing the stopped launcher, and freezes that group before cleanup. Linux/Android use child-subreaper lineage. Linux signals group-external descendants only through start-time-revalidated pidfds, verifies that a matching lifetime descriptor really owns a shared `flock` through bounded `fdinfo`, reaps descendants, and confirms both group and captured-identity disappearance. Android fails closed without a stable signal handle. macOS registers `kqueue` fork/exit history before provider code runs and fails closed after any provider fork or premature exit. The double-fork/`setsid` regression clears the runtime environment and closes the lifetime descriptor; Linux still captures it through guardian lineage, while macOS retains recovery-required authority.
- Startup observation revalidates executable and workspace authority before `Adopted`. A fresh adapter distinguishes locked, unlocked, missing, and failed lease observation. Only the guardian's exact generation-bound `gone` receipt proves Unix absence; an unlocked `unix` marker stays ambiguous even when group, tag, and lifetime signals are absent. An exact owned runtime with uncertain health or filesystem authority becomes `LeaseUncertain`, which persistence commits as disconnected/recovery-required without discarding its handle, owner, or start intent. Runtime adoption alone still cannot claim a provider conversation active; a successful start does so only after the separate Codex thread-attachment result is durably validated.
- The local executable-race tests cover application and updater races under a trusted OS account. A malicious process already running as the same account is outside the threat boundary; this is especially relevant on macOS, which lacks Linux-style sealed descriptor execution.
- Startup closes the persistence read transaction before driver observation, then reloads the complete session and reservation set and applies only an exact-CAS observation before network admission.
- Antigravity and OpenCode return a visible unavailable error in this slice; they do not fall back to print, exec, Python, or another provider.
